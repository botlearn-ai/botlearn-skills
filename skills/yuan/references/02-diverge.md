# 02 · 场景展开 · 发散 · 收敛

阶段 2、5、6。核心纪律：**先发散到够宽，再收敛到能拍板**。技法按需挑，够用即止。

---

## 1 · 场景与角色展开（阶段 2）

### 1.1 角色 × 环节矩阵

横轴是业务环节（按事情的生命周期排，如 发现 → 上报 → 受理 → 分派 → 处置 → 反馈 → 督办 → 复盘），纵轴是角色（含原话没提但一定会卷进来的，如领导、外部平台、被投诉对象）。每格写三样：**做什么 / 卡在哪 / 要什么**。空格本身就是发现。

### 1.2 冲突与优先级表（多角度思考的落点）

按利益相关方逐个看还不够，价值在于**找出彼此打架的地方**。需要时再加两个维度：专业领域（法务 / 技术 / 运营 / 财务各怎么看）、时间（上线第 1 周 / 第 3 个月 / 第 2 年，各方诉求怎么变）。

| 冲突 | A 方要 | B 方要 | 先满足谁 | 理由 / 折中 |
|---|---|---|---|---|
| 例：快 vs 准 | 居民：报了马上有人接 | 受理员：先审核防误报 | 试点期 B，之后按类别放开 | 误派比慢更伤信任 |

至少写 3 条。写不出冲突，通常是角色还没分细，或者只写了大家都同意的话。

### 1.3 边界与反例清单（逐项过一遍）

| 类别 | 问自己 |
|---|---|
| 重复 | 同一件事多人报、同一人反复报怎么办？ |
| 质量 | 照片模糊、定位不准、描述不清？ |
| 误用与恶意 | 报着玩、报私怨、刷单、借平台骚扰？ |
| 归属 | 不归我管的、归属有争议的、跨部门的？ |
| 时间 | 夜间、节假日、高峰期、超时、反复超时？ |
| 结果 | 处理不了、处理完又反弹、上报人不认可结果？ |
| 人员 | 接单人请假、离职、调岗；领导换人？ |
| 数据 | 上报人隐私、被拍者隐私、数据留存期限、对外公开范围？ |
| 环境 | 弱网、老人不会用、没有智能手机？ |
| 考核副作用 | 指标设了以后，大家会怎么"优化"指标而不是解决问题？ |

最后一类最常被漏掉，也最致命：超时考核会催生"先结单再说"。

## 2 · 发散技法（阶段 5）

### 2.1 形态先判：现成 / 改造 / 组合 / 自研

| 信号 | 走法 |
|---|---|
| 有成熟产品正好覆盖，且采购可行 | **直接用** |
| 有现成底座，差一块 | **改造**：在已有平台上加模块 |
| 几样小工具拼起来就够 | **组合**：如 小程序表单 + 工单系统 + 消息推送 |
| 都不合适 | **自研**，但设计要吸收调研结论 |

来源：search-first 的 Adopt / Extend / Compose / Build。别默认自研。

### 2.2 先常规、后反转（反常识假设）

1. 先老老实实写出**行业惯常答案**（大多数人会怎么做），一段话即可。
2. 找出它依赖的**最核心的一条假设**，反过来，重做一遍。
   - 例：惯常是"超时就提醒领导"，假设是"慢在队员"。反过来："如果慢的根本不在队员呢？"→ 推出"先改派单路径"。
3. 列 3–5 个"**假如……会怎样**"：假如没有预算？假如必须一周上线？假如用户不用手机？假如对手免费？假如规模扩大 100 倍？每条一句结论，有价值的进三条走法。

### 2.3 第一性原理

明确写一句"**忽略行业惯例**"，然后只问：要改变的那件事，物理上 / 组织上最少需要什么？
- 把需求拆到不能再拆的事实（例：居民要的是"问题消失 + 知道它消失了"，不是"一个 App"）。
- 从这些事实往上重新搭方案，再和惯常答案对比，差异处就是潜在的新定位或打法。
- 产出不必全对，但必须和常规清单**至少有一处实质不同**，否则说明还在惯例里打转。

### 2.4 强制三条走法

| 走法 | 要求 |
|---|---|
| 最小可行 | 最快能用起来，两周量级，砍掉一切非必需 |
| 理想形态 | 长期最好，数据和流程都理顺 |
| 横向一招 | 换个框法，往往最便宜（例：不做新系统，改流程或改考核） |

每条写：一句话概述 / 工作量（S/M/L/XL）/ 风险 / 优点 2–3 条 / 缺点 2–3 条 / 复用了什么现成的东西。横向一招优先从 §2.2 的反转和 §2.3 的第一性原理里取。

### 2.5 让点子更野一点的技法（创造三法则：反常识假设见 §2.2，另两条在这里）

- **反向思维**：先想"这个系统怎样会彻底失败、没人用"，再倒推必须有的东西。
- **跨界混搭**：外卖派单、快递轨迹、医院分诊、客服工单——别的行业怎么处理同构问题？至少点名 2 个行业各借一个机制。迁移前查语境能不能搬（政务的问责逻辑和商业不同）。
- **限制激发**：把限制变成设计驱动（"队员不愿多装 App" → 全部走已有的政务 IM）；也可以主动加一条苛刻限制（"零开发"、"一周上线"）逼出新解法。
- **相邻可能**：核心能力做成后，还能顺手解决什么？（上报数据 → 热点地图 → 巡查排班）
- **野一点的样例**：
  - 平淡："增加分类筛选，提高处理效率。"
  - 有意思："上报时自动比对过去 30 天同位置记录，第三次出现就直接升为'顽疾'，进中队长周会议程。"
  两条都是结果导向，第二条才让人"哦"一声。先把有意思的版本提出来，再让用户删减。

## 3 · 推理工具（需要严谨时用）

- **逐步推演**：沿着一单的生命周期，一步步问"这一步谁做、凭什么做、做不了怎么办"。
- **多路径择优**：同一问题出 2–3 种解法再比，不一次定死。
- **自我验证**：写完一个结论，主动找一个反例来打它。

## 4 · 收敛与取舍（阶段 6）

### 4.0 四象限初筛

发散出的点子先按**影响（大/小）× 难度（易/难）**放进四格：

| | 易 | 难 |
|---|---|---|
| 影响大 | 先做（进 MVP） | 规划（进理想形态） |
| 影响小 | 顺手做或放发散清单 | 不做（进不做清单） |

每个点子落格时写一句理由。"影响"按深层意图衡量，不按热闹程度。

### 4.1 对比表

维度按题目增删，常用：

| 维度 | 看什么 |
|---|---|
| 解决核心痛点 | 是否直击深层意图，不只是表层功能 |
| 上手成本 | 每个角色要多学什么、多装什么 |
| 对接现有系统 | 需不需要打通、打通难度 |
| 可追责与可见性 | 过程是否留痕、谁能看到什么 |
| 防滥用 | 重复、恶意、刷指标 |
| 工作量与周期 | 人月、依赖 |
| 合规与数据 | 隐私、留存、等保信创 |
| 可演进 | 先做小的，后面能否长大 |

### 4.2 取舍铁律

- **互补而非替代**：标杆不全对，明确写出"不建议抄的"和理由。
- **抄机制不抄内容**：抄"同位置聚合去重"这个机制，不照搬别人的字段名和界面。
- 每个"抄 / 留 / 不做"都写理由。
- 推荐必须落到一个决定上，并附 **MVP 范围** 和 **不做清单**。
