# 01 · 需求解构 · 前提挑战 · 定义"好"

阶段 0–1。目标：开始搜和想之前，先把"到底要解决什么、题目本身对不对、做成什么样算好"说清楚。

---

## 1 · 需求解构（阶段 0）

### 1.1 四问 + 现状

| 维度 | 问题 | 常被漏掉的点 |
|---|---|---|
| 表层需求 | 原话说了什么？ | 原话里的动词往往就是功能清单（"上报""接单""看进度""提醒"），先逐个拆出来 |
| 深层意图 | 真正想改变什么？ | "做个上报入口"背后常是"转手太多、过程看不见、责任说不清" |
| 隐含约束 | 受众、组织、合规、预算、已有系统、上下游？ | 政务要等保/信创/数据不出域；已有 12345、网格化平台要不要对接 |
| 成功标准 | 做成什么样算好？谁来判？ | 不同角色的"好"不一样：居民要快和看得见，领导要考核数据 |
| **现状** | 没有这个东西时，大家怎么凑合？ | 转几道手、谁在中间受累、每天多少量、多久才处理完——这决定了痛点有多真 |

现状追问来自 gstack office-hours 的 Status Quo：如果答案是"现在没人管、也没人抱怨"，痛点可能没那么痛。

### 1.2 写回理解

把四问的答案写成一段短说明给用户看，**用户明说的和你推断的分两栏**。推断的部分最容易错，也最值得用户纠正。

### 1.3 澄清问题的纪律

- 至多 2–3 个，只问会改变方向的（受众是谁、要不要对接已有系统、预算量级）。
- 每个问题附推荐默认值，让用户否决而不是作答。
- 能自己查到的不问；用户说"直接做"就不问，把问题挪进文档的"待确认"。

## 2 · 前提挑战（阶段 1 前半）

展开方案之前先问四件事：

1. **这是对的问题吗？** 换个框法会不会简单得多？（例："做个 App" vs "在已有小程序里加一个入口"）
2. **什么都不做会怎样？** 痛是真实的还是想象的？
3. **已经有什么在部分解决它？** 现有系统、现有流程、现成产品。
4. **东西做出来，用户怎么拿到？** 下载 App、扫码、公众号、嵌进已有平台——分发路径决定了能不能用起来。

结论写成 2–4 条"前提"，形如：

```
前提 1：居民上报入口应挂在已有的城市服务小程序里，而不是单独做 App —— 认 / 否？
前提 2：……
```

用户否掉某条 → 回到 §1 修正理解。

## 3 · 定义"好"（阶段 1 后半）

把成功标准翻成**能直接判对错的检查项**，自审时逐条核对。

| | 例子 |
|---|---|
| ✔ 好的检查项 | "每个角色都写了至少一个痛点和一个诉求"；"每条竞品机制都有来源链接"；"给出了不做清单"；"三条走法里有一条两周内能上线" |
| ✘ 太模糊 | "分析全面""调研深入" |
| ✘ 太脆弱 | "必须提到某某产品" |

检查项可以后补，也要迭代：跑完发现某项永远能过（没区分度），换掉。

### 3.1 默认检查项（脑爆文档）

| # | 检查项 |
|---|---|
| C1 | 一页结论里有明确推荐，可以直接说"好/不好" |
| C2 | 用户说的 / 推断的分开标注 |
| C3 | 角色 × 环节矩阵覆盖了所有原话里出现的角色 |
| C4 | 边界与反例 ≥ 8 条，且每条给了处理思路 |
| C5 | 竞品机制每条写成"某某靠什么机制"，且有来源 |
| C6 | 至少一个开源仓库读过代码（不只 README），写明 LICENSE |
| C7 | 三条走法，含最小可行；有不做清单 |
| C8 | 反方证据或失败案例 ≥ 2 条 |
| C9 | 事实 / 推断 / 建议可区分；无来源的标"未核实" |
| C10 | 待确认问题都附推荐默认值 |
| C11 | 冲突与优先级表 ≥ 3 条，每条写了先满足谁和理由 |
| C12 | 有"常规 vs 反转"与第一性原理推导，且至少一处结论和常规清单实质不同 |
| C13 | 智囊团 ≥ 3 席，每条意见标了采纳/不采纳及去处；无编造的名人原话 |
| C14 | 追问记录 3–5 层，被问穿的点已进风险表或改了推荐 |
