# 03 · 合成产物 · 配套工程 · 可容错 · 安全 · 发布

Deliver 阶段（阶段 6）。把调研与技术选择落成"可用产物 + 让它真正在生产里活下来的一切"。

---

## 1 · 合成产物

- 依 `references/01-research-and-benchmark.md` §6 的取舍表 + `references/02-technique-library.md` 的技术选择，写出优化后的 prompt / skill 正文。
- **保留差异化、植入互补短板**：自己强的（如声音/聚焦）不丢，抄来的（如字段规格/基调分档）成建制补上。
- 产物必须**可直接复制运行**；给用户看的字段零行话，术语只留在内部推导层。
- **不要改变用户的使用习惯**：复杂度锁在产物文件里，不要转嫁给用户。产物从 20 行进化到 200 行、能力翻几倍，用户那句话应该一个字都不用改。

---

## 2 · 配套工程要求（最常被忽略、最影响真实效果）

**产物本身只是冰山一角。**交付时必须一并列出"产物之外要落地"的工程项。按需取用：

### 2.1 数据与上下文

1. **上游字段**：产物依赖的输入是否已由**确定性规则层**算好并传入（如基调档位 `day_tone`）？**档位判定用规则、不用随机数。**
2. **上下文注入**：需要的历史/状态是否传入（如 `recent_hooks` 支撑防重复）？
3. **跨对话记忆**：需要"接着上次继续"的产物，单独维护一个记录文件（如 `history.json` 记上次处理到哪），存在**稳定目录**（项目/用户目录），避免升级时被删。

### 2.2 可容错三件套（假定一定会出意外）

> 永远不要假设用户会按你期望的方式使用产物。他会给空文件、给 PDF、给超长文本、用你想不到的说法触发。

1. **开头检查输入**：动手前先看一眼——空的？格式不在支持列表？太短？太长？不对就提醒用户，别硬着头皮往下跑。
   ```
   ## 第一步：检查输入
   - 没有提供内容 → 询问用户
   - 少于 100 字 → 提醒"内容较短"
   - 格式不在支持列表（如只支持 Markdown 却传了 PDF）→ 提醒转换格式后重试
   - 超过 10000 字 → 建议先指定重点
   ```
2. **关键步骤人工确认**：容易走偏的地方停一下等确认。方向错了才发现，前面全白做。
3. **中间结果随手存文件**：别让所有产物只活在对话里。生成图片那步失败了，前面写好的提示词还在磁盘上；翻译中途出错，已译段落还在，下次从断点继续。

### 2.3 解析与输出

4. **解析兜底链**：Schema 校验（含关键字段非空/合规）→ 校验失败重试 1 次 → 仍失败回退**确定性静态兜底**（按 用户ID+日期 做种子，保证同人同输入稳定）。
5. **客户端/下游约定**：如"某字段为空则隐藏该栏"——偶尔出现的提醒才被当真。
6. **文件纪律**（多步骤产物必守）：
   - 产出文件与输入文件**放同一目录**，一个项目的中间产物聚在一起，流程脉络一眼可见；
   - 遇到同名文件**先备份再覆盖**（`xxx-backup-YYYYMMDD.md`）。成本为零，能避免事后捶桌子。

### 2.4 长期

7. **迭代机制**：定期抽查线上坏输出，把新的空洞句式追加进黑名单；把引发问题的用例固化进题库（见 `references/04-validate-and-iterate.md` §2）。
8. **许可与合规**：借用开源代码的 LICENSE（AGPL 有传染性）；面向市场的合规底线——健康只谈状态不下病症、财务不给操作指令、重大决策不下结论。

## 3 · 安全（本地执行的产物必守）

产物赋予智能体真实的操作特权。本地运行时能读写文件、执行脚本和命令行——**能力越大，安全越不能马虎**。要防两类风险：**防坏人**（第三方恶意产物）与**防自己**（自己写的新产物有逻辑漏洞，删错文件）。

### 3.1 三道闸

| 闸 | 做法 |
|---|---|
| **最小权限** | 只给完成当前任务所需的权限。只需读就不给写；只需一个目录就不给整个硬盘 |
| **二次确认** | 高风险操作（删除、发送、执行未知代码、访问敏感数据）执行前暂停等确认 |
| **可追溯** | 操作留痕：读了什么、改了什么、调了什么工具。配合 Git 可随时回退 |

### 3.2 四个好习惯

1. **安装前先安检**（别人的产物）：读一遍 SKILL.md 和 `scripts/`，重点查 5 项——从哪读/写到哪/是否联网/是否拉外部 URL；脚本里有没有隐藏的删除、覆盖、上传、外联；生成物会不会直接覆盖原文件；是否以任何借口索要密码密钥；安装依赖时**核对库名拼写**（当心把热门库名拼错一个字母的恶意包）。
2. **第一次跑用假数据**：新脚本极易"覆盖原文件""全选删除"。先用测试文件跑通，再上真实数据。
3. **建专属文件夹**：永远在专门新建的目录里让智能体干活，不要在桌面或系统根目录。
4. **看清弹窗再点**：二次确认框强迫自己读完命令再允许，别像装软件那样狂点下一步。

> **额外注意**：从外部 URL 获取数据的产物风险最高——即使产物本身可信，它拉回来的内容也可能含恶意指令。

### 3.3 按风险分层

| 风险 | 特征 | 措施 |
|---|---|---|
| 低 | 只读、纯文本处理 | 常规 |
| 中 | 写文件、调外部 API | 限定目录 + 输出前预览 |
| 高 | 删除、发送、支付、改配置 | 强制二次确认 + 留痕 + 先备份 |

## 4 · 发布（三种场景，要求逐级叠加）

### 4.1 个人自用
过一遍 §3 的安全清单即可。重点：读写目录是否超出必需范围、不可逆操作是否有二次确认、覆盖前是否先备份。

### 4.2 团队共享
- **怎么分发**：提交到团队仓库（如项目的 `.claude/skills/`）自动获取；规模大了搭内部市场，让成员自选安装，避免把所有产物塞进每个人的上下文。
- **怎么保质量**：不必设审核委员会，但要有"**发布前有人真用过并觉得好用**"的机制。

### 4.3 社区发布

用户决定装不装，通常不超过一分钟，只关心三件事：简介看不看得懂、有没有示例判断效果、装完能不能跑通。

**发布前清单**

- [ ] **重审 description**：面向陌生人，一句话说清干什么，覆盖常见触发说法
- [ ] **说明文档**：功能说明 + **使用示例（最易忽略也最有用：输入什么→输出什么）** + 依赖说明 + 兼容性
- [ ] **清理个人信息**：搜索 `key` `token` `password` 和绝对路径，确认无残留；依赖密钥的改用 `<YOUR_API_KEY>` 占位符并在文档醒目处提示配置
- [ ] **加版本号**：frontmatter 加 `version`，初版 `v1.0.0`
- [ ] 含私密密钥、专属接口、敏感本地路径的产物，**不要上架公开社区**

**发布之后**

- 留意反馈（Issues、评论、评分），持续迭代。
- **向后兼容**：公开发布后尽量不改核心触发词与固定输出字段——改了，正在用的人会受影响。新增功能优先走外挂扩展。
- 长期不维护的，在文档里标注"已停止维护"并推荐替代方案，比放着不管好得多。
