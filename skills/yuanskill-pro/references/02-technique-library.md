# 02 · 提示词技术库 · 输出模板 · 约束分层 · skill 形态的字段级工程

Develop 阶段（阶段 5）用。**核心纪律：按任务类型挑技术，够用即止**——把所有技巧全塞进一个产物是反模式。

---

## 1 · 技术库（四类增强）

### 推理增强（复杂分析、逻辑推导）
- **CoT 思维链**：要求逐步展示推理。
- **ToT 思维树**：先生成多条路径再择优。
- **Self-Consistency 自一致**：多次推理取多数一致解。
- **自我验证 / Verification Loop**：输出后附检验步骤，主动找漏洞。

### 创造增强（创意生成、方案设计）
- **类比推理**：从别的领域借成熟模型。
- **反向思维**：先想"什么会让它失败"。
- **约束重构**：把限制条件转成设计驱动力。
- **跨域迁移**：把 A 领域的机制搬到 B 领域（注意文化/语境是否可迁移）。

### 结构增强（长文本、多步骤）
- **任务分解**：复杂目标拆成有序子任务。
- **角色分层**：主角色 + 批评者角色交替（生成/审稿）。
- **格式锚定**：明确指定输出结构（JSON/Markdown/列表）。
- **分层规划**：先纲后目。
- **强制先出计划**：模型边做边想容易"狗熊掰棒子"——做到后面忘了前面。多步骤任务里插一步"先把清单列全再动手"，人脑不需要，但对稳定性很关键。

### 精确增强（高准确率的专业任务）
- **少样本示例**：2–3 个高质量范例（含"差/好"对比更佳）。
- **边界声明**：明确哪些情况不适用 / 遇到 X 该怎么办。
- **不确定性标注**：让模型标低置信度内容（confidence 字段**必须配评分标准**，否则模型恒定输出 0.7）。
- **Schema 校验**：输出结构可机器校验。

## 2 · 按复杂度/类型组合（配方）

```
if 任务复杂/需推理:  选 CoT (+ToT/自一致) + 自我验证 + 迭代精修；补 类比示例 + 失败模式分析
if 需创造/设计:      加 发散思维 + 约束重构 + 跨域迁移 + 差好示例
if 精确关键:         加 格式锚定 + Schema 校验 + 多阶段检查 + 纠错
if 多步骤易跑偏:     加 强制先出计划 + 关键步骤人工确认
按 Creative→多视角+语气  Technical→约束+精确  Educational→少样本+清晰结构  Complex→CoT+系统框架 分流
始终优化: 够用即止、token 效率、鲁棒性
```

角色分配：给模型一个**具体、专业、有边界**的身份（避免空泛的"世界顶级专家"）；必要时加"影子角色"（批评者/审稿人）做二次把关。

## 3 · 输出模板与约束分层

### 3.1 输出模板（按复杂度取舍）

```
[角色定义]   具体、专业、有边界的身份（人格 or 职能，视目标而定）
[任务目标]   单一清晰目标，避免多目标混淆
[背景上下文] {{填充位}} / 数据来源说明
[执行要求]   逐条、可验证
[输出格式]   精确规范 + 示例（JSON 给 key 顺序）
[约束与边界] 不要做什么；遇到 X 时该怎么办
[质量自检]   输出前勾选：□覆盖所有显式要求 □格式合规 □无明显错漏 □可追溯
[踩坑点]     用中发现的反复犯的错（第一版可以空着）
```

### 3.2 约束写三层，不要平铺

| 层 | 内容 | 判定 |
|---|---|---|
| **铁律** | 极少数"违反即视为本次输出无效"的底线（不越权判断、不出现禁用术语、只返回纯 JSON、每条基于给定输入） | **必须能自动判定违反与否** |
| **规范** | 其余偏好类写作规则 | 尽量遵守 |
| **踩坑点** | 事后使用中才暴露的盲区 | 见 `references/04-validate-and-iterate.md` §4 |

平铺无优先级会让模型分不清底线与偏好；**约束条数与执行力成反比**。

### 3.3 两条写法纪律

**① 正面描述与禁止清单必须配对。**
正面负责牵引方向（往哪儿走），禁止负责兜底（不能碰红线）。
- 只有正面 → 模型在细节上踩雷；
- 只有红线 → 模型不知往哪儿走。
> 例：设计类需求既写"参考《经济学人》图表页、麦肯锡研报"（正面），也写"不要默认配色、不要所有卡片一个样、不要纯装饰渐变"（红线）。

**② 给方向优于给参数。**
在模型能力覆盖的领域，把微观决策权还给模型。
- 写死"主色深蓝、间距 16px、圆角 8px" → 模型退化成模板填充器；
- 只给"偏麦肯锡研报风格，避免后台系统风格" → 它自主补全字体、间距节奏、阴影层级、交互反馈，常常超出预期。

**配套判据——何时该给参考样板**：模型当前的任务，是否**必须有一份"照猫画虎"的参考物**？没有就别加（过早引入＝无谓复杂度），有才按需挂载。给**样板**（"大致长这样，有这些可选组件"），不给死模板。

## 4 · skill 形态的字段级工程

产物是 skill 时**必须过一遍这一节**。这些不是风格偏好，是运行机制决定的硬约束。

### 4.1 description：唯一的触发决策依据

所有已安装 skill 的 description 会在启动时注入系统提示词。**它的首要读者是模型，不是人。**

```
description = 功能定义 + 触发场景/触发词
```

- **贴合用户实际表述**，覆盖高频说法。不写"处理数据"，写"处理 CSV/Excel 数据，用户提及数据统计、报表生成时触发"。
- **去人称代词**：`我可以帮你处理 Excel 文件` ✘ → `处理 Excel 文件并生成报告` ✔。人称会让模型混乱"谁是我、谁是你"。
- **控制篇幅**：100 字左右，最多不超过 200。装的 skill 越多，这份预算越紧张。
- **模型有"工具调用惰性"**：天生倾向于不用 skill、自己硬上。所以要主动覆盖用户可能的说法，而不是等着被精确命中。
- **反向触发词**（装 20 个以上 skill 时才需要）：一句话点明最易混淆的场景。`…不用于润色已有中文内容，不用于改写或摘要`。

> ⚠️ **触发条件写进正文等于白写。**正文是第二层，只有触发之后才被读取，那时决策已经做完了。

### 4.2 三层渐进式披露（Progressive Disclosure）

| 层 | 内容 | 开销 |
|---|---|---|
| 第一层 | YAML 前置信息（name + description） | 启动即常驻，体量小 |
| 第二层 | SKILL.md 正文 | 触发后**全文加载并常驻到对话结束**，还消耗一次工具调用 |
| 第三层 | `references/` `scripts/` `assets/` | 走到那一步才读；脚本在沙盒跑，只回一行结果 |

由此推出的硬规格：

- **正文克制**：≤ 5000 词元（中文约 3800 字）、≤ 500 行。厚重背景与完整 API 规范一律拆到第三层。
- **引用只一层，不嵌套**：不要 A 引 B、B 又引 C。层级越深模型越容易迷路，开销越不可控。
- **只放不提 = 不会被读**：放进 `references/` 却没在正文写"何时读哪个文件"，模型不会主动去找。必须写成 `条件 + 相对路径`：`如需填写表单，先读取 references/forms.md 并按其步骤操作`。

### 4.3 目录结构

```
your-skill-name/          # 文件夹名必须与 frontmatter 的 name 一致
├── SKILL.md              # 必需
├── references/           # 可选：按需读取的参考文档
├── scripts/              # 可选：框架直接运行，不经过模型
└── assets/               # 可选：模板、样板等静态资源
```

### 4.4 两个可扩展设计（跑通之后再考虑，别提前做）

- **维度组合替代穷举**：不列举 N 种风格，而是拆成若干互不干扰的维度（如构图/配色/渲染/密度/情绪/文字布局），各有几个取值。维护 30 个选项能产生上万种组合，新增一个维度值自动适配其余维度。
- **外挂扩展文件**：让用户不改主文件就能定制。查找顺序：项目级 `.<skill>/EXTEND.md` → 用户级 `~/.<skill>/EXTEND.md`。**扩展文件必须放项目/用户目录，不能放安装目录**——升级会覆盖。

## 5 · 模型 / 脚本分工

### 5.1 任何任务拆成三类操作

| 操作 | 交给谁 | 例子 |
|---|---|---|
| **执行规则**（规矩定一次，之后都一样） | **脚本** | 金额保留两位、日期统一 YYYY-MM-DD、格式校验 |
| **做判断**（没有固定答案，看情况） | **模型** | 哪些趋势值得关注、结论怎么写、重点放哪 |
| **调外援**（智能体没有的能力） | 工具 / MCP | 连数据库、生图、抓网页 |

分工粒度不是"按步骤"，而是"**按性质**"——同一步里两类操作可以并存。

### 5.2 唯一判据

> **同样的输入，是否应该产生同样的输出？**
> 是 → 用脚本（模型是概率预测，做死规则会出偏差）。
> 否 → 用模型 + 参考样板。

**反例提醒**：边界情况多到写不全的读取/解析类任务（多工作表、编码不一、表头异常），**给指引比写死脚本更合适**——让模型看到具体数据再灵活判断。别把"能用脚本"误解成"必须预置脚本"。

### 5.3 何时补领域知识文件

当模型的结论**"正确但外行"**时（算出 ROI 1.39 却不知道低于 1.5 通常意味着亏损），它缺的不是能力而是领域常识。这时在 `references/` 加一份领域知识文件，写入基准值、常用维度、行业惯例，**并在正文写明何时读它**。

## 6 · 平台差异（同一意图，落法略不同）

- **Claude**：长上下文、显式推理框架、XML/分节结构友好。
- **GPT 系**：结构化分节、对话起手式。
- **Gemini**：创意/对比类任务。
- 未知平台：套通用最佳实践。
- skill 形态遵循 Agent Skills 开放标准，跨框架基本通用，但迁移时仍需针对平台差异适配。
