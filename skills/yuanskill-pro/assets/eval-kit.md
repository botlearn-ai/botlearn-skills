# 评测工具包（可直接复制使用）

配合 `references/04-validate-and-iterate.md` §2 使用。四张模板：测试用例 / 检查项 / 记分表 / 变化清单。

**存放约定**：题库单独建档，**不要写进产物正文**。建议放在产物同级的 `evals/` 目录或项目目录下，不要放安装目录（升级会覆盖）。

---

## 1 · 测试用例模板

```markdown
# <产物名> 题库
> 最后更新：YYYY-MM-DD ｜ 用例数：N（正例 x / 反例 y）

## 用例 01 · <一句话场景>  [正例]
- **指令**：帮我整理一下昨天产品评审会的纪要        ← 要像真人说话，别写"请使用 X 技能"
- **输入**：`fixtures/meeting-30min.txt`（30 分钟转录稿）
- **期望结果**：按模板格式输出，含决议事项与待办清单
- **来源**：初版设计 / 2026-08-16 线上失败案例

## 用例 02 · <口语 + 长输入>  [正例]
- **指令**：这个讨论记录太长了，帮我提炼重点
- **输入**：`fixtures/brainstorm-90min.txt`（含大段闲聊）
- **期望结果**：提炼核心讨论点与结论，过滤闲聊

## 用例 03 · <容易混淆的场景>  [反例·不应触发]
- **指令**：帮我把这段话改得更通顺              ← 与产物沾边，实际需要的是别的能力
- **期望结果**：不触发本产物
- **备注**：反例要拿真正容易混淆的，别用"写个斐波那契函数"凑数
```

## 2 · 检查项模板

```markdown
## 检查项（v1，YYYY-MM-DD）
| # | 检查项 | 类型 | 判定方式 |
|---|--------|------|----------|
| C1 | 产物被正确触发 | 触发 | 观察是否加载 |
| C2 | 输出包含「待办事项」小节且每条有负责人 | 格式 | 逐条核对 |
| C3 | 篇幅不超过原文 30% | 量化 | 字数比 |
| C4 | 未编造原文没有的人名/数据 | 事实 | 抽查比对 |
```

写检查项的判据：
- ✔ 能直接判对错 · ✘ "输出质量好"（太模糊）· ✘ "必须出现某句精确措辞"（太脆弱）
- 检查项本身要迭代：没区分度的（有没有产物都能过）删掉换一个。

## 3 · 记分表模板

```markdown
## 记分：用例 01 ｜ v2 vs <基线>   YYYY-MM-DD
> 基线选择：首次评测＝「不用产物」；版本升级＝「改之前的旧版本」

| 检查项 | 基线 | 新版 | 依据（必填，不许只写"不通过"） |
|--------|------|------|------------------------------|
| C1 触发 | —   | ✅   | 说"帮我整理一下"即触发 |
| C2 待办有负责人 | ❌ | ✅ | 基线 3 条待办全无负责人；新版 3/3 均有 |
| C3 篇幅 ≤30% | ❌ | ❌ | 原文 3000 字 → 输出 1800 字，占比 60% |
| C4 无编造 | ✅ | ✅ | 抽查 5 处均可回溯 |

**主观验收**（检查项查不到、但一看就不对的）
- 讨论过程写得像流水账，重要决定埋在细节里
- ✔ 记法：具体、可执行 ｜ ✘ 记法："质量太差""太死板"

**耗时**：基线 5s ／ 新版 28s —— 质量提升明显，耗时可接受 / 需优化

**结论**：通过 / 不通过 → 下一步只改一个问题：______（治本写法，不是窄补丁）
```

## 4 · 变化清单模板

```markdown
# CHANGELOG · <产物名>

## vN（YYYY-MM-DD）
**一句话**：这一版只解决 ______ 一个问题。

### 抄了什么（来源必填）
- <机制> ← 来源：<标杆/章节/文件>；理由：补了 ______ 短板

### 保留了什么（差异化，明确不动）
- <能力> —— 这是相对标杆的优势，抄了会退化

### 新增了什么（自研）
- <内容> —— 动机：______

### 明确没抄
- <项> —— 理由：______

### 评测结果
- 用例数 N，通过 x/y；基线对比：______
```
